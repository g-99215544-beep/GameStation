# Cannon Battle (Meriam) — Design

Date: 2026-07-28

## Context

Groups currently race through their station rotation in isolation. Their only
interaction is the finish-order bonus at the Smart Board. Teachers want a
direct, playful way for groups to affect each other during the hunt.

The cannon adds that. A group finds a hidden **cannon QR** somewhere on the
school grounds, solves the question behind it, and earns **one cannonball**.
From the map they can fire that cannonball at any other group, knocking a
fixed percentage off that group's **HP**. HP multiplies the group's station
marks at the end, so being shot genuinely costs them.

Decisions locked during brainstorming:

- **HP is subtractive, marks are multiplied at the end.** HP starts at 100 and
  each hit subtracts `damagePercent` (default 10). Final marks =
  `round(totalScore × hp/100) + finishBonus`. Compounding (`hp × 0.9`) was
  rejected: 72.9% is a hard number to explain to a ten-year-old.
- **HP has a floor of 50%.** A group that gets picked on cannot be wiped out.
- **The finish bonus is not damaged.** It rewards speed, not battle.
- **Multiple cannon QRs; one ball per group per QR.** With three cannon QRs
  every group can hold at most three cannonballs. A global first-come-first-
  served race was rejected — it needs an online lock and punishes groups whose
  rotation reaches that area last.
- **Redeeming a cannon QR requires 100% correct**, and awards **no marks**.
  The cannonball is the whole reward. Awarding marks would turn cannon QRs
  into a way to farm score without visiting a station. Failing is not
  punished — the group can rescan and retry.
- **All cannon UI lives in a panel on the map**, opened from a cannon icon.
  The station clue screen's password box keeps meaning "the station you are
  standing at" and is not overloaded.
- **Firing requires internet. Earning a cannonball does not.** Stations
  already work fully offline; cannon questions match that. Only the shot
  itself needs the network.
- **Groups that have opened their chest (`status === 'won'`) cannot be shot.**
  Their final marks are already announced.
- **No other targeting limits.** Any group may fire at any other group, any
  number of times, at any moment.
- **The victim's video never interrupts an active station game.** A shot
  landing mid-game is held and played the moment that game ends.
- **Both videos are re-encoded to 720p** before shipping. `0728.mp4` is
  1920×1080 at 9.3 Mbps — 10 MB for 8.4 seconds, precached onto every phone.

## Architecture

A new `cannon/engine.js` holds the pure logic — damage arithmetic, the
cannonball ledger, and the pending-hit queue — with `cannon/engine.test.js`
beside it. This matches `battleship/engine.js`, `stations/layout.js` and
`offline/store.js`, which are all pure modules with `node:test` suites while
their UI lives in `index.html`.

Two alternatives were considered and rejected:

- **Everything inline in `index.html`.** The file is already 4,179 lines and
  227 KB, and the damage arithmetic — the part most likely to be wrong —
  would be untestable.
- **Cannons modelled as hidden stations.** `order`, `currentIndex`,
  `rotationOrder`, `isJourneyDone` and the station-count clamp all assume
  every station sits in the rotation. Threading an exception through them
  risks regressions in code that is currently stable.

## Data model

### Config

```
config/cannon
  enabled        boolean
  damagePercent  number   1..50, default 10

config/cannons/<cid>
  id           string
  name         string
  password     string   exactly 5 chars [A-Za-z0-9]
  gameType     string   one of GAME_TYPES
  gameDataRaw  string   same shape as a station's
```

`damagePercent` is the only battle number a teacher can change. The 50% HP
floor is `CannonEngine.MIN_HP`, a constant, not config — it is a safety rule
for children rather than a tuning knob, and keeping it out of the database
means it cannot drift between hunts. The admin card displays it as fixed text.

At most **6 cannons** per hunt (`CannonEngine.MAX_CANNONS`), matching the
station cap. "＋ Tambah Meriam" disables at the limit.

A cannon password is generated by the existing `generateStationPassword()` and
validated to be unique against every station password **and** every other
cannon password. `pushConfig()` refuses to save on a clash and names the
offending cannon.

### Progress

New fields on `progress/<gid>`, alongside the existing `currentIndex`, `keys`,
`completedStations`, `totalScore`, `status`:

```
hp        number   50..100, default 100
ammo      number   unfired cannonballs, default 0
claimed   { <cid>: timestamp }        cannon QRs already redeemed
incoming  { <pushId>: { from, ts, damage, hpAfter } }   unwatched hits
```

`incoming` is the victim's inbox. A record stays there until the victim has
actually watched the video, so a closed app, a dead battery, or a dropped
connection never swallows a hit.

## The stale-HP hazard

`submitCompletion()` currently writes the whole progress object:

```js
const next = OfflineStore.advanceProgress(progress, {...});  // { ...base, ... }
db.ref(path).update(next)
```

`advanceProgress` spreads the local `progress` object, so `next` carries every
field the phone last knew about. If a group is shot while their phone is
offline, their cached `progress` still says `hp: 100`. Finishing the next
station would write that stale 100 back over the damaged value and silently
undo the hit.

Three measures close this:

1. **The victim never writes their own cannon fields.** `submitCompletion`
   strips `hp`, `ammo`, `claimed` and `incoming` from the payload before
   `update()`. `cannon/engine.js` exports `stripCannonFields(payload)` and a
   unit test asserts the payload is clean.
2. **Damage is applied by the shooter, via a transaction** on
   `progress/<victim>/hp`. Two groups firing at the same victim in the same
   second both land.
3. **Ammo is spent by a transaction** on `progress/<shooter>/ammo`. If the
   transaction aborts (already zero, e.g. two tabs), no shot is fired. If the
   damage step then fails, the ammo is refunded.

Local `hp` and `ammo` are read from the live Firebase listener when online and
from the progress cache when offline, but they are never merged back into the
payload the phone writes.

## Arithmetic

```js
applyDamage(hp, damagePercent, minHp)     // max(minHp, hp - damagePercent)
effectiveScore(totalScore, hp)            // round(totalScore * hp / 100)
finalScore(totalScore, hp, finishBonus)   // effectiveScore(...) + finishBonus
```

`openChestOnBoard()` changes from `(p.totalScore||0) + bonus` to
`CannonEngine.finalScore(p.totalScore||0, p.hp==null?100:p.hp, bonus)`. Hunts
saved before this feature have no `hp` field; a missing `hp` is read as 100, so
old hunts score exactly as they did.

`renderSmartBoard()` shows the HP-adjusted running total for groups that have
not yet opened their chest, so the live ranking is honest.

A new card in Step 2 (Pengurusan Stesen), below the station blocks:

```

☑ Aktifkan meriam untuk hunt ini
   Damage setiap tembakan:  [ 10 ] %      HP minimum: 50%

   ┌ Meriam 1 ───────────────────────────────┐
   │ Nama       [ Meriam Kubu Batu        ]  │
   │ Password   [ K7F2M ]                    │
   │ Jenis Soalan  [ Lembaran Kerja     ▾ ]  │

   │ [ ▶️ Uji ]   [ 🗑 Buang ]                 │
   └─────────────────────────────────────────┘
   [ ＋ Tambah Meriam ]
```

With the checkbox clear, nothing changes for students — the map shows no
cannon icon and the panel does not exist.

Cannon QRs are generated and printed in Step 4 (QR Tersembunyi) in their own
labelled section, visually distinct from station QRs so a teacher does not tape
the wrong sheet to the wrong wall.

`testStation()` gains a cannon equivalent so a teacher can play through a
cannon question from the setup form without saving or scanning.

### Worksheet-editor key refactor

The worksheet editor is keyed by station number: `getWorksheetQuestionsFromEditor(i)`,
`renderWorksheetEditor(i, questions)`, `setWorksheetImageFromFile(i, index, file)`,
and element ids such as `ws_q_${i}_${index}` and `worksheet_editor_${i}`.

These take a **string key** instead of a number: stations pass `"1"`..`"6"`,
cannons pass `"c1"`, `"c2"`. Nothing else about the editor changes. This is the
alternative to duplicating the whole image-paste/crop/compress editor for
cannons, and it is confined to the id-building expressions.

## Student UI

### Cannon panel

A 💣 button in the corner of the map, rendered only when `config/cannon.enabled`.

```
┌─ ⚔️ MERIAM ─────────────────────────┐
│  Peluru anda:  💣 💣        (2)     │
│  [ 📷 Scan QR Meriam ]              │
│  ─────── Pilih sasaran ───────      │
│  Kumpulan 2   ▓▓▓▓▓▓▓▓▓░  90%  [🔥] │
│  Kumpulan 3   ▓▓▓▓▓▓▓▓▓▓ 100%  [🔥] │
│  Kumpulan 5   ▓▓▓▓▓░░░░░  50%  [🔥] │
│  Kumpulan 7   🏆 sudah buka peti    │
└─────────────────────────────────────┘
```

The group's own row is omitted. `won` groups are listed but not firable. With
zero cannonballs the target list is shown greyed with "Cari QR meriam untuk
dapat peluru". Offline, 🔥 is disabled with "Perlu internet untuk menembak"
while the Scan button stays live.

Target HP comes from a `huntRef('progress').on('value')` listener that is
attached only while the panel is open, then detached — 14 groups of small
objects, and it does not run during station games.

### Earning a cannonball

Scan → match against `config/cannons` by password → if `claimed[cid]` exists,
show "Peluru meriam ini sudah anda ambil" → otherwise open the question through
the existing `renderGame()` with a `_cannonMode` flag set.

In `_cannonMode`, `submitCompletion()` routes to `finishCannonQuestion()`. A
perfect answer awards `ammo + 1` and sets `claimed[cid]`; anything less shows
"Belum tepat — cuba lagi" and the group may rescan. Neither outcome touches
`totalScore`, `currentIndex`, `keys` or `completedStations`.

`submitCompletion` is the hook, not `finishGame`: six game types — Sifir,
Crossword, Battleship, Jejak Lari, Sudoku and Tangram — call `submitCompletion`
directly and never pass through `finishGame`.

"Perfect" is per game type, because the scoring scales differ. Lembaran Kerja,
Sudoku, Crossword and Battleship are percentages, so the bar is 100. Tangram
scores out of 200 (three shapes at 40 each, plus up to 80 for speed), so the bar
is all three shapes with no speed requirement. Sifir and Jejak Lari derive their
score from the time remaining and can almost never reach 100, so for those the
bar is the game's own success flag plus a non-zero score — both score exactly 0
when the student fails. The table lives in `CannonEngine.PASS_SCORE`.

Offline, the write goes through `queuePendingWrite()` exactly as a station
completion does, and the local progress cache is updated immediately.

### Firing

1. Guard on `isOffline()`.
2. Transaction `progress/<me>/ammo`: abort if `< 1`, else decrement.
3. Transaction `progress/<victim>/hp`: `applyDamage(hp, damagePercent, MIN_HP)`.
   Abort if the victim's `status === 'won'`.
4. Push `{ from, ts, damage, hpAfter }` to `progress/<victim>/incoming`.
5. Play `assets/cannon/fire.mp4` full-screen.

If step 3 or 4 fails, the ammo is refunded by an incrementing transaction and
the student sees "Tembakan gagal — peluru dipulangkan".

A group whose own `status` is `'won'` cannot fire either — their hunt is over.
The cannon icon is hidden on the chest screen, and unspent cannonballs simply
expire. Symmetry with the no-shooting-a-winner rule is the point: once a
group's marks are announced, they are outside the battle in both directions.

### Receiving a hit

The student holds `huntRef('progress/'+gid+'/incoming').on('child_added')` for
the whole session, from login onwards.

| Where the victim is | What happens |
|---|---|
| Map, clue screen, result screen | Prompt appears immediately |
| Inside a station game (`view-game`) | Held; flushed when `showResult()` runs |
| Offline | `child_added` fires on reconnect |

Because a hit landing during a game is deliberately held, `finishGame()` is not
disturbed and the station timer is never paused.

The `incoming` node is deleted **after** the video finishes. If several hits are
waiting, one video plays with a combined caption: "Anda ditembak 2 kali! HP: 80%",
and all the pending nodes are cleared together.

Once the group's `status` becomes `'won'`, any records still sitting in
`incoming` are cleared **without** playing. Their damage was already applied to
HP when the shot was fired, so the marks are correct; replaying a battle
animation over the celebration screen would only confuse.

### The tap gate

Both clips carry AAC audio. The shooter's video follows a tap, so it plays with
sound. The victim's does not — mobile browsers block autoplay with sound, and
both fullscreen and `screen.orientation.lock()` require a user gesture too.

So the victim gets a card first:

```
┌─────────────────────────────┐
│           💥                │
│   Kapal anda ditembak!      │
│      oleh Kumpulan 3        │
│                             │
│    [ Ketuk untuk lihat ]    │
└─────────────────────────────┘
```

One tap grants audio, fullscreen and orientation lock together.

### Landscape playback

The overlay is fixed, `inset: 0`, black, above everything. On open it requests
fullscreen and tries `screen.orientation.lock('landscape')`. Where that is
unavailable (Safari on iOS), a portrait viewport instead rotates the video
`90deg` with CSS and sizes it to the viewport's shorter edge, so the clip fills
the screen sideways either way. A skip button fades in after 2 seconds.
`prefers-reduced-motion` skips the video entirely and shows the caption card,
matching how `playDailyIntro()` already behaves.

### HP bar on the ship

A separate `#journeyShipHp` element positioned by `placeJourneyShip()`, not a
child of `#journeyShip`. The ship applies `scaleX(-1)` when sailing left, which
would mirror a nested bar.

```
   ▓▓▓▓▓▓▓▓▓░  90%
       ⛵
```

Green `var(--green)` for remaining HP, red for the lost portion, with the
percentage beside it. When HP drops the bar pulses red once.

### HP elsewhere

- **Cannon panel** — per target, as above.
- **Smart Board** — an HP bar on each chest card; displayed marks are already
  HP-adjusted.
- **Admin dashboard** — an HP column beside station progress.

## Offline behaviour

| Situation | Behaviour |
|---|---|
| Scan cannon QR offline | Works fully. Question renders from the config cache; `ammo`/`claimed` are written locally and queued via `queuePendingWrite()`. |
| Fire offline | Blocked, with "Perlu internet untuk menembak". |
| Shot while offline | `child_added` fires on reconnect; the card appears then. |
| HP shown offline | Last known value, with the existing connectivity badge indicating it may be stale. |

## Media

Re-encoded with the ffmpeg already installed on the author's machine:

```
ffmpeg -i <src> -vf scale=-2:720 -c:v libx264 -crf 26 -preset slow \
       -c:a aac -b:a 96k -movflags +faststart <dest>
```

| Destination | Source | Before | Expected after |
|---|---|---|---|
| `assets/cannon/fire.mp4` | `Pirate_cat_fires_cannon_at_202607252212.mp4` | 1.7 MB | ~0.9 MB |
| `assets/cannon/hit.mp4` | `0728.mp4` | 10.0 MB | ~1.3 MB |

Both are added to `LOCAL_ASSETS` in `sw.js` and `CACHE_NAME` is bumped to
`gs-shell-v10` so existing installs fetch them. Total precache goes from about
3.4 MB to about 5.6 MB. The original MP4s at the repo root are left untouched.

## Database rules

`database.rules.json` gains range validation:

```
progress/$gid/hp     number, 50..100
progress/$gid/ammo   number, 0..99
config/cannon/damagePercent  number, 1..50
config/cannons/$cid  requires name, gameType, password matching /^[A-Za-z0-9]{5}$/
```

This guards against corrupt writes from a bug or a bad sync. It is **not** a
security control: the database has no auth and `.write` is open to anyone with
the URL until the configured expiry. That is the app's existing posture and this
feature does not change it.

## Testing

**`cannon/engine.test.js`** — `node:test`, following `battleship/engine.test.js`:

- `applyDamage` stops exactly at 50 and never goes below, for any damage value
  and any number of hits
- `isPerfect` uses the right bar for every game type, including Tangram's 120
  and Sifir's success flag
- `effectiveScore` rounding, including `totalScore = 0` and `hp = 50`
- `finalScore` leaves `finishBonus` undamaged
- missing `hp` is treated as 100, so pre-feature hunts score unchanged
- redeeming the same cannon id twice adds one cannonball, not two
- several `incoming` records collapse into one summary with the correct count
  and the lowest `hpAfter`
- `stripCannonFields` removes `hp`, `ammo`, `claimed` and `incoming` and leaves
  every other field intact — the guard against the stale-HP hazard

**`tests/cannon.spec.js`** — Playwright with a seeded fake Firebase, following
`tests/student-island-journey.spec.js`:

- admin enables cannons, adds one, saves, and the config round-trips
- a duplicate cannon/station password is rejected with a named error
- a student scans a cannon password, answers 100%, and gains one cannonball;
  `totalScore` is unchanged
- a cannon question of a type that bypasses `finishGame` still never advances
  the journey
- rescanning a redeemed cannon shows the already-claimed message
- the cannon panel lists other groups with HP and hides the student's own group
- firing decrements ammo and reduces the target's HP by `damagePercent`
- a `won` group is listed but not firable, and a `won` group sees no cannon icon
- the HP bar renders above the ship at the correct width
- offline, 🔥 is disabled and the Scan button stays enabled
- adding a 7th cannon is blocked at the `MAX_CANNONS` limit

## Out of scope

- Shields, repairs, or any way to regain HP.
- Cannons aimed at a specific station rather than a group.
- A battle log or history screen. The Smart Board HP bars are the record.
- Cannon marks contributing to `totalScore`.
